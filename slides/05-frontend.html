前端 — IFU 流水化（F0/F1/F2+Fp/F3）

  • F0：PC 投机推进：每拍假设 pc_q + 4；taken 分支由 F3 自重定向回卷
  • F1：MMU 地址翻译：16 项全相联 iTLB + PTW(page table walker) 子 FSM
  • F2 + Fp：ICache 控制：F2 驱动请求；Fp 深度 4 环形 FIFO 追踪 in-flight 响应
  • F3：预测 + 后端交付：输出 32-bit 指令；驱动 Predict；生成 fe_take_branch

F1 PTW 子状态机：idle / req / waitResp / drain

squash 与 drain 的必要性

前端在“识别一条指令”之前，必须先完成两步：先地址翻译，再按物理地址取指。 因此我把相关流程拆成多个阶段：F1 负责 MMU/PTW，F2 负责 ICache 访问，F3 负责指令预解码、分支预测、交付后端。

  • waitResp: 等待 ptw 响应，将要得到的物理地址有效
  • drain: 等待 ptw 响应，但是将要得到的物理地址无效

若 F3 识别到无条件跳转，说明此前 F1/F2 可能已被错误路径污染，此时需要通过 squash 让 F1 放弃当前 PTW 事务。 但 PTW 事务一定发起，那必须完成响应，否则后续请求会阻塞，进而导致死锁，所以我设置了 drain 状态。

F3 分支预测：GShare + IJTC + RAS

GShare

RAS

预测器 结构 触发 更新
GShare 直接映射 条件分支 提交时
IJTC 全相联 JALR (非 ret) 提交时 + FIFO 替换
RAS 栈 call/ret F3 出队时即时
算法简述： GShare 用 idx = PC[low] ⊕ GHR 索引、2-bit 饱和计数器预测方向； IJTC 以 JALR PC 为 tag 全相联匹配目标地址，未命中回退到顺序流； RAS 在 call 时 push 返回地址、ret 时 pop 作为预测目标。
省去 BTB 的取舍：在 4 段流水前端中，JAL/BR 目标 = PC + imm 可在 F3 一拍直算；仅 JALR 需 IJTC/RAS。 省去 BTB 的存储开销与维护逻辑。
RAS 在 F3 即时 push/pop —— 推测路径上 call/ret 仍成对出现，不破坏栈。 降低函数调用密集场景的预测延迟。

推测性控制冒险与自重定向

为降低前端复杂度，前端不专门处理强制 serializing 指令： ecall/ebreak、mret/sret、sfence.vma、fence.i、CSR 写。 这类指令由后端在提交阶段触发全局 flush 并回传权威 PC。
设计取舍：serializing 指令在实际程序中占比极低，依据 Amdahl 定律， 不值得为其在前端引入复杂专用优化路径。

PC 更新三来源与优先级

后端权威 PC（flush / redirect） > 前端预测 PC（F3） > 顺序 PC（pc + 4）
优先级多路选择保证：出现异常/序列化事件时以后端结果为准；无冲突时走预测，最后回退到顺序推进。
